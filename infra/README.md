# claw infra

**How changes reach claw:** agents (the assistant as `openclaw`, Claude Code as `coder`) push `agent/*` or `claude/*` branches through `agent-git`, which runs as `gitbot`, the only holder of a write token. The owner merges on GitHub. `claw-sync` resets `~/.openclaw` to `origin/main` within about a minute of a merge (timer every minute) and restarts the gateway only when `openclaw.json` changes (see Safe deploys).

**Claude Code:** OpenClaw's acpx starts it with `sudo -n -u coder /usr/local/bin/coder-acp`. sudo strips the gateway's environment, so coder only sees its own read-only token. It works in `/srv/work/<repo>` and follows `coder-CLAUDE.md`, installed root-owned as Claude Code's managed memory file `/etc/claude-code/CLAUDE.md` (every coder session loads it, ACP-started ones included: Claude Code loads managed memory whatever `settingSources` says; coder can't change it). It applies to every Claude Code user on the host, so the admin user running `claude` there gets coder's instructions too. Check with `/memory` in a coder session, or ask an ACP-started session to quote a line from its instructions. The ACP adapter it runs is pinned by `acp/package-lock.json` (exact versions and hashes for the whole tree) and installed root-owned at `/usr/local/lib/claw/acp` by `sudo claw-install`, so nothing is downloaded when a session starts and coder can't change it. **Upgrading it** is a PR: in `infra/acp/`, set the new version in `package.json`, run `npm install --package-lock-only --ignore-scripts`, commit both files, merge, then `sudo claw-install` (it reinstalls only when the lockfile changed, with `npm ci --ignore-scripts`, and keeps the old install if that fails). **Plan usage:** `claude-usage` (root-owned in `/usr/local/bin`, run as coder; openclaw may run it through `coder.sudoers`) prints the 5-hour and weekly utilization and reset times as JSON. It uses the Agent SDK's structured `get_usage` request (the data behind `/usage`) from that same pinned install, starts no model call, and caches answers for 10 minutes in coder's `~/.cache` (`--fresh` skips the cache). coder can write that cache, so a cached answer is re-validated before it's printed: only the known fields, each in a strict format (ISO timestamps, a lowercase plan name, plain model names), otherwise it reads fresh. A prompt-injected Claude Code session can't use the cache to pass text to the assistant. The SDK marks that request experimental; it can only change when the lockfile is bumped, and `claw-smoke`'s `claude-usage` check catches a bump that breaks it. Exit 3 means coder's login has no plan limits (an API key or a setup token without the profile scope): log in again interactively as coder. Try it: `sudo -u coder claude-usage`.

**State backup:** `USER.md`, `MEMORY.md`, `DREAMS.md` and `memory/` are agent-owned and gitignored in claw-config. `claw-backup` (nightly ~03:30, as openclaw) copies them into a local repo at `~/.openclaw/state-backup` (one commit per day with changes) and pushes it through `agent-git` to the private `claw-state` repo on branch `agent/state/<hostname>`. agent-git only pushes `agent/*`/`claude/*` and opens PRs, so the first run opens one PR on claw-state that then just gets updated each night. **The branch is the backup; don't merge or delete it.** Activate with `sudo claw-install` (see Applying infra). Test right away: `sudo systemctl start claw-backup && sudo journalctl -u claw-backup -n 20`. **History can only grow:** agent-git never force-pushes `agent/state/*`. It takes those branches only from openclaw (coder and others are refused) and only to `claw-state`, which takes no other branches. If `~/.openclaw/state-backup` is ever missing (rebuilt host, partial copy, `rm -rf`), the next run builds a fresh repo, agent-git refuses the push as a non-fast-forward (logged as `PUSH-REFUSED non-fast-forward`), and `claw-backup` exits with an error and pings `/fail` on `HEALTHCHECKS_PING_URL` with the reason. So you hear about it and no snapshot is lost (claw-sync's next success ping marks the check up again). Fix it by restoring the repo from the branch (steps below), not by deleting anything. **What the agent can still do:** the assistant runs as openclaw and can call `agent-git pr claw-state agent/state/<hostname>` itself, so a confused or prompt-injected agent could append a bad snapshot. It can't rewrite or delete the earlier ones. A GitHub ruleset (`agent/state/**`: Block force pushes, Restrict deletions) would add the same guarantee server-side, but rulesets need GitHub Pro for a private repo. Pulling a copy now and then is still worthwhile (step 2 below works anywhere coder's token does). When moving hosts, the `rsync` of `~/.openclaw` brings `state-backup` along so history continues (check it arrived before the first nightly run); a host with a different name moves that history onto its own branch `agent/state/<newname>` and leaves the old branch alone.

**Restoring state** (as the admin user on the host; the admin has no GitHub credentials, so the clone uses coder's read-only token, which covers claw-state):
1. `sudo systemctl stop claw-backup.timer` so a nightly run can't recreate `state-backup` mid-restore.
2. `sudo -H -u coder git clone -q -b agent/state/<hostname> https://github.com/andrewgarmon/claw-state.git /tmp/claw-state`
3. Move any existing repo aside first, or `cp -a` nests into it: `S=/home/openclaw/.openclaw/state-backup; [ -e "$S" ] && sudo mv "$S" "$S.bad.$(date +%s)"; sudo cp -a /tmp/claw-state "$S" && sudo chown -R openclaw: "$S" && sudo rm -rf /tmp/claw-state`
4. Copy the files into the workspace as openclaw (the admin can't write there): `sudo -H -u openclaw bash -c 'cd ~/.openclaw/state-backup && cp -a USER.md MEMORY.md DREAMS.md memory ~/.openclaw/workspace/'` (leave out any that aren't in the backup).
5. `sudo systemctl start claw-backup.timer`, then `sudo systemctl start claw-backup && sudo journalctl -u claw-backup -n 20` should show either "nothing new to push" or a push of the restored head (a fast-forward, so no history is lost).

**Safe deploys:** `claw-sync` runs `openclaw config validate` before restarting. Invalid config is never deployed. After a restart it waits up to 3 min for `openclaw gateway health` to pass; if it doesn't, it resets to the last commit the gateway was healthy on and restarts again. Either way that `origin/main` commit is marked bad and skipped until main moves, so fix it with a new PR. Exceptions: a commit already known good (e.g. reverting local drift) is never marked bad, and if the rollback doesn't recover the gateway either, nothing is marked bad and the commit is retried next run. A `pending` marker is written before a config change touches the tree; if a run is killed mid-deploy (reboot, OOM, timeout), the next run re-validates, restarts, re-checks health and rolls back if needed. While main is marked bad, local drift is still reverted (to the last good commit). **Untracked files** (anything in the checkout that git neither tracks nor ignores, e.g. a new `workspace/*.md` or skill) count as drift: claw-sync removes them (ignored state such as `.env`, `USER.md`, `memory/` and `state-backup/` stays). What's ignored comes only from the `.gitignore` committed at HEAD: nested `.gitignore` files, `.git/info/exclude` and `core.excludesFile` are not consulted, since the agent's user can write them. A run that removes anything fails its ping with "untracked files removed: <paths>", listing up to 20. `agents.defaults.skipBootstrap: true` stops OpenClaw re-seeding its starter files (`SOUL.md`, `IDENTITY.md`, `BOOTSTRAP.md`, ...) when they're missing, so a removed starter file doesn't come back and fail every run. To keep such a file, add it to the repo by PR. The state dir is writable by `openclaw` (the agent's user), so `good`/`pending` are only trusted if they're on `origin/main`; a forged `bad` can still freeze deploys, but that keeps sending `/fail` until cleared. A `git fetch` failure only sends `/fail` after 15 runs in a row (about 15 minutes), so a short GitHub or network blip stays quiet. State lives in `/home/openclaw/.cache/claw-sync/{good,bad,pending,fetch-fails,last-full}`. If a commit was marked bad by a transient failure, clear it and re-run: `sudo -u openclaw rm /home/openclaw/.cache/claw-sync/bad && sudo systemctl start claw-sync`. PRs also run `.github/workflows/ci.yml`: the same config validation, every `infra/tests/*.test.sh` (claw-sync, claw-backup, claw-install, claw-smoke, ...) and `infra/brokers/*/test.sh`, a secret scan, a personal-words check, a state-file guard and shellcheck. The personal-words check greps the tree, tracked paths, and each commit a PR or push adds (diffs and messages) for the words in the `PERSONAL_DENYLIST` repo secret (one word or phrase per line, case-insensitive, whole words). It prints only file:line or commit ids, never the word, and skips when the secret isn't set (fork PRs never get it). It catches pushes that skip `agent-git`'s `redact.txt` check, like the owner's own commits. On PRs it runs the base branch's copy of `.github/scripts/personal-denylist.sh`, so a PR can't change what runs with the secret. Don't list words the repo legitimately contains, such as the GitHub username in URLs. A new test file is picked up without a workflow edit. Agents can't write `.github/workflows/`, so changes to CI come from the owner (or Claude in the app).

**Dead-man alerts:** claw-sync runs every minute. A full run checks gateway health and pings `HEALTHCHECKS_PING_URL` from `~/.openclaw/.env`: success when synced and healthy, `/fail` (with the reason as the body) on a bad deploy, a rollback, an unhealthy gateway, removed untracked files or a claw-sync crash. While idle (HEAD == `origin/main`, no drift, nothing pending, main not marked bad), a run only fetches and exits quietly unless the last successful full run was 5+ minutes ago, so pings still arrive about every 5 minutes. A deploy, a drift revert or a failed last run always gets a full run. The time of the last successful full run is in `last-full` in the state dir. The agent can write it, but a forged value can only bring a full run forward or stop the pings (which alerts); it can never skip a deploy or a drift revert. If the host, the timer or claw-sync stops, the pings stop. In healthchecks.io set the check to period 5 min, grace 10 min. To deploy right away instead of waiting up to a minute: `sudo systemctl start claw-sync` (if nothing changed, it exits quietly and logs nothing). Test (clearing `last-full` forces a full run): `sudo -u openclaw rm -f /home/openclaw/.cache/claw-sync/last-full && sudo systemctl start claw-sync && sudo journalctl -u claw-sync -n 5`, then look at the check's event log.

**Stale-backup alert:** `claw-backup` touches `~/.cache/claw-backup/last-ok` on every successful run, including nights with nothing new. A claw-sync full run fails its ping with "claw-backup hasn't succeeded in <N>h" while that file is over 26h old (or missing), and keeps failing until a backup succeeds. This catches a backup that never runs (timer disabled, unit broken before the script starts), which claw-backup's own `/fail` can't. `claw-install` creates the file if it's missing, so a new host gets 26h before its first nightly run. The file is agent-writable, so the agent could hide staleness; it can't affect deploys, and the owner still sees the backup branch's dates on GitHub.

**Smoke test:** `sudo claw-smoke` checks the live wiring that CI's fakes can't, and `claw-install` runs it at the end of every install. A failure doesn't undo the install, but it's the last line and `claw-install` exits non-zero. It prints `PASS`/`FAIL <check>: <reason>`/`SKIP` per check:
- `acp-adapter`: starts `coder-acp` the way acpx does (`sudo -u openclaw sudo -n -u coder`), sends ACP `initialize` and checks the reported version against `acp/package-lock.json`. Covers the sudo rule, the root-owned install and the pin. No network, no Claude usage.
- `claude-usage`: runs `claude-usage --fresh` as openclaw through the sudo rule and checks for a weekly utilization. Skipped (not failed) when coder's login has no plan limits.
- `agent-git-token`: `agent-git issue-list` on the config repo as openclaw, one read-only GitHub API call. Catches an expired or revoked gitbot token before a PR fails.
- `agent-git-refusals`: a state-backup push as coder and a `claude/*` push to claw-state as openclaw must both be refused. Both are refused before any network access; each leaves a `DENY` line (branch names `*/claw-smoke`) in agent-git.log.
- `timers`: `claw-sync.timer` and `claw-backup.timer` are enabled, active and have a next run.
- `gateway`: `~/.openclaw` is at `origin/main` (as of claw-sync's last fetch) and `openclaw gateway health` answers.
- `plugins`: OpenClaw's plugin registry (`openclaw plugins list --json --enabled`, as openclaw) has only ids from `plugins.allow` enabled, none from the workspace extensions dir, and each root-owned plugin enabled from its dir under `/usr/local/lib/claw/openclaw-plugins/`. Prints plugin ids only.
- `tools`: the deployed `openclaw.json` denies `group:runtime`, `gateway`, `cron` and `skill_workshop`, has `tools.fs.workspaceOnly: true`, and allows every tool the installed claw-tools plugin declares. Skipped until claw-tools is installed.
- `agent-cal`: one read-only `calendars` call, skipped if the broker or its secret isn't there.

It only reads, or makes calls that are refused before the network: it never pushes, messages Telegram, creates events or calls a model, and it never prints command output, only its own reasons.

## Applying infra
**This folder is NOT auto-applied.** After merging a change here, run on the host as the admin user:
`sudo claw-install`

It clones `origin/main` fresh into a root-only temp dir (using coder's read-only token, read but never sourced), shows the `infra/` commits and diffstat since the last install (`d` shows the full diff), asks, runs `install.sh` from that clone, records the commit in `/var/lib/claw-install/last`, deletes the clone, updates itself and runs `claw-smoke` (see Smoke test). `-y` skips the question. Root never runs anything from `/home/openclaw/.openclaw`: the assistant's user can write that tree between claw-sync resets, so a prompt-injected assistant could otherwise edit `install.sh` (or a sudoers file it installs) and get root the next time it ran. `install.sh` itself refuses to run from any tree that isn't entirely root-owned, so the old `sudo bash /home/openclaw/.openclaw/infra/install.sh` now stops with a pointer here. **Root never writes under a service user's home** (openclaw, coder, the broker users): what a service needs from this repo is installed root-owned under `/etc`, and anything in a home is created as that user (`infra/lib/service-home.sh`).

**First time on a host** (installs `claw-install` from a fresh clone, never from the openclaw checkout; asks for a token if coder's isn't set up yet):
```bash
sudo bash -c '
  set -e; umask 077; d=$(mktemp -d); trap "rm -rf $d" EXIT
  T=$(sed -n "s/^GH_TOKEN=//p" /home/coder/.config/coder.env 2>/dev/null | head -1)
  [ -n "$T" ] || { read -rsp "Read-only GitHub token for claw-config: " T; echo; }
  GH_TOKEN=$T git -c credential.helper= -c "credential.helper=!f() { echo username=x-access-token; echo password=\$GH_TOKEN; }; f" \
    clone -q --depth 1 https://github.com/andrewgarmon/claw-config.git "$d/r"
  install -m 755 -o root -g root "$d/r/infra/claw-install" /usr/local/sbin/claw-install
  echo "installed /usr/local/sbin/claw-install"'
sudo claw-install
```

**Changing live config by hand** (e.g. `openclaw plugins install`): run `sudo systemctl stop claw-sync.timer` first, make the change, PR the resulting `openclaw.json`, merge, then `sudo systemctl start claw-sync.timer`.

## Adding a broker
A broker is a dedicated user that holds one secret and lets the assistant (or coder) run a fixed set of verbs with it through sudo, so the agent never sees the secret. `gitbot`/`agent-git` is one. To add another, create `infra/brokers/<name>/` and change nothing else (not `install.sh`, not CI):
- `broker.conf`: data, parsed with a strict `KEY=value` regex and never sourced (`infra/lib/broker-install.sh` documents the keys). `USER` (its own user: no two brokers may share one, root, the admin user, openclaw and coder are refused, and an existing account is only reused if it looks like one claw-install made, i.e. system UID, nologin, home `/home/USER`, no group but its own), `CALLERS` (from `openclaw coder`), `SECRET` (a file name under `/home/USER/.config/`, mode 700 dir), optional `DEPS` (apt packages) and `PYREQS` (one `name==version --hash=sha256:…` line per package, covering every transitive dependency and every wheel pip may pick on the host, installed into a venv with `--no-deps --require-hashes`, wheels only).
- `agent-<name>`: the wrapper, installed root:root 755 to `/usr/local/bin/`. It sets `PATH` and `HOME` itself, sets `BROKER`, `BROKER_USER` and `LOG`, sources `/usr/local/lib/claw/broker.sh` by that absolute path, calls `broker_require_user` first, reads its secret with `broker_secret_raw` or `broker_secret_env` (never `source`), validates every argument and logs the caller and verb (never the secret or bodies).
- `test.sh`: CI runs it automatically. `brokers/git/test.sh` shows how to point a copy of the wrapper at the repo's `broker.sh`, a temp `HOME` and fake tools.
- optional `lib/`: support files, installed root:root to `/usr/local/lib/claw/brokers/<name>/` (its venv lives there too).

`claw-install` then creates the user and config dir, installs deps, the wrapper, `lib/` and the venv, generates `/etc/sudoers.d/agent-<name>` (`Defaults!… env_reset, !setenv` plus one `CALLER ALL=(USER) NOPASSWD: /usr/local/bin/agent-<name>` line per caller), checks it with `visudo -cf`, and prints a TODO while the secret file is missing. Every `broker.conf` is validated before anything changes. Then write the secret as the broker user with the `read -rsp` pattern under Secrets.

**Removing a broker:** delete its dir and run `sudo claw-install`. It removes the generated `/etc/sudoers.d/agent-<name>`, `/usr/local/bin/agent-<name>` and `/usr/local/lib/claw/brokers/<name>/` (only files carrying the generated header), so the sudo grant never outlives its config. The user and its secret stay until you delete them (`sudo deluser --remove-home <user>`).

**When not to use one:** a low-value key, or one that's only good for what the assistant does anyway, can stay in `~/.openclaw/.env`. A plain HTTPS API key may be better served by OpenClaw's secret egress proxy (check its docs). Use a broker when the secret opens more than the task needs (an Apple app-specific password also opens iCloud Mail), when you want the agent limited to a few verbs, or when a prompt-injected assistant holding the secret would be a real problem.

## Public repos (agent-git)
agent-git treats a repo as public if GitHub says so (it asks on every write, so a repo flipped to public is covered right away) or if it's listed in `/home/gitbot/.config/public-repos` (one name per line, `#` comments; for a repo you're about to flip). For public repos:
- **Writes are coder-only.** `pr`, `issue`, `issue-comment`, `issue-label`, `issue-close` and `issue-reopen` are refused for anyone but coder. The assistant hands public work to Claude Code, which can't read the assistant's memory. Reads (`issue-list`, `issue-view`) stay open.
- **Everything that would go public is checked first.** For `pr`: every commit not already on the default branch (message, author and committer, and every line it adds, including new file paths), the branch name, title and body. Removed lines aren't checked, since they're already public, so a PR that deletes a leaked string still goes through. Branches with merge commits are refused; rebase instead. For issues: the title, body or comment. The checks are `/home/gitbot/.config/redact.txt` (one string per line, matched case-insensitively; `#` comments and blank lines are ignored) and gitleaks (Ubuntu's package, installed by claw-install; `gitleaks:allow` markers are neutralized so an agent can't opt out). On a hit nothing is written. The caller and the log get which part and which check (e.g. `DENY refused: … the body contain a redact.txt entry`), never the matched text.
- **It fails closed.** If `redact.txt` is missing or has no entries, gitleaks fails to run, or GitHub can't say whether the repo is public, nothing is written. Private repos behave exactly as before, apart from that one visibility lookup.
- `new-repo` still only creates private repos. Making a repo public is your manual step.
- **The leak check is the real control; coder-only is a speed bump.** The assistant starts Claude Code and writes its prompt, so a prompt-injected assistant could still pass private details through it. Keep `redact.txt` complete rather than relying on who the caller is.
- **Commit identity matters.** Author and committer are checked, so coder must commit as `Claude Code <claude@claw.invalid>` (claw-install sets that). Commits made under your own name can't go through agent-git to a public repo; push those yourself.
- Limits: entries are exact strings apart from case, so `Jane Q Example` doesn't catch `jane-q-example` or `janeqexample` (add the variants you care about). Compressed or binary content is checked as raw bytes, so a string inside an image or archive gets through (keep binaries out of public repos). Entries match inside longer words, so prefer full names and handles over short words.

Set up after `sudo claw-install` (it creates gitbot's config dir), before any repo goes public:
```bash
sudo -u gitbot bash -c 'umask 077; touch ~/.config/redact.txt ~/.config/public-repos'
sudoedit -u gitbot /home/gitbot/.config/redact.txt    # your Telegram user ID, bot username, email addresses, full name, family names, street, phone
sudoedit -u gitbot /home/gitbot/.config/public-repos  # optional
```
Check it once the public repo exists: ask Claude Code to file an issue on it with one of your redact entries in the title. It should be refused with "contain a redact.txt entry", and `sudo tail -2 /home/gitbot/agent-git.log` should show the DENY without the string.

## Secrets (not in git, set up per host)
- gitbot: fine-grained PAT, All repositories, Administration + Contents + Issues + Pull requests read/write (Issues is for the `agent-git issue*` commands), everything else (esp. Workflows, Secrets) no access.
  `sudo -H -u gitbot bash -c 'umask 077; read -rsp "Token: " T && printf "%s\n" "$T" > ~/.config/gh-token'`
- calbot (`agent-cal`, the assistant's calendar access over CalDAV): an Apple app-specific password from account.apple.com → Sign-In and Security → App-Specific Passwords. It isn't scoped (it also opens iCloud Mail, where password resets land), which is why only calbot holds it.
  `sudo -H -u calbot bash -c 'umask 077; read -rp "Apple ID: " U && read -rsp "App-specific password: " P && printf "APPLE_ID=%s\nAPPLE_APP_PASSWORD=%s\n" "$U" "$P" > ~/.config/caldav.env'`
  Test: `sudo -u calbot agent-cal calendars` and `sudo -u calbot agent-cal events --days 2`; log in `/home/calbot/agent-cal.log`. Every create/update/delete is kept with a copy of the event as it was in `/home/calbot/state/history.json` (last 200): `sudo -u calbot agent-cal changes` lists them and `sudo -u calbot agent-cal undo [--change cN]` reverses one. Then remove the old webcal URL (the file is openclaw's, so as the admin user): `sudo -u openclaw sed -i '/^APPLE_CALENDAR_URL=/d' /home/openclaw/.openclaw/.env`. Optional extra layer: give the assistant its own Apple ID, share your calendars to it with "Can edit", and use that ID's password, so a leak only exposes an empty inbox.
- coder: fine-grained PAT, All repositories, Contents + Issues + Pull requests read-only.
  `sudo -H -u coder bash -c 'umask 077; read -rsp "Token: " T && printf "GH_TOKEN=%s\n" "$T" > ~/.config/coder.env'`
  plus git setup: a credential helper that reads `GH_TOKEN` from that file. claw-install sets the commit identity `Claude Code <claude@claw.invalid>` (needed for public repos, see Public repos).
- coder's Claude login: as coder, `curl -fsSL https://claude.ai/install.sh | bash && ~/.local/bin/claude` (log in with the Claude subscription).
- openclaw: read-only deploy key on claw-config (`~/.ssh`), git identity `Assistant <assistant@claw.invalid>`. Gateway, Telegram and Gemini credentials live inside `~/.openclaw` (`.env`, auth profiles).
- openclaw `.env` per-person values: `TELEGRAM_ALLOW_FROM` is your numeric Telegram user ID. `openclaw.json` uses it for `channels.telegram.allowFrom` and `commands.ownerAllowFrom`. Not a secret, but it differs per install, so it stays out of git. **If it's missing, Telegram ignores everyone** (OpenClaw leaves `${TELEGRAM_ALLOW_FROM}` unresolved with a warning, which matches no one) and config validation still passes, so claw-sync deploys anyway. Fix: add it, then `sudo -u openclaw XDG_RUNTIME_DIR=/run/user/$(id -u openclaw) systemctl --user restart openclaw-gateway`.
  `sudo -H -u openclaw bash -c 'F=~/.openclaw/.env; read -rp "Telegram user ID: " I && [[ $I =~ ^[0-9]+$ ]] || { echo "not numeric"; exit 1; }; [ -s "$F" ] && [ -n "$(tail -c1 "$F")" ] && echo >> "$F"; printf "TELEGRAM_ALLOW_FROM=%s\n" "$I" >> "$F"'`

## Moving to a new host (e.g. the Pi)
1. Base OS (arm64 is fine): an admin user with sudo, SSH keys only, Tailscale, ufw allowing only tailscale0. Add swap if RAM is under 8 GB. On a Pi, boot from a USB SSD, not the SD card.
2. System-wide Node 24, user `openclaw`, OpenClaw installed as openclaw (npm prefix `~/.npm-global`), `openclaw onboard --install-daemon` (local, loopback, port 18789), `sudo loginctl enable-linger openclaw`.
3. **Stop the gateway on the OLD host first.** Two gateways polling one Telegram bot will conflict.
4. Copy state as openclaw: `rsync -a old:/home/openclaw/.openclaw/ ~/.openclaw/` and `old:/home/openclaw/.ssh/` (deploy key). This brings config, `.env`, memory, sessions and installed plugins.
5. Install `claw-install` and run it (First time on a host, above), then do the TODOs it prints (Secrets above).
6. Restart the gateway, check `openclaw logs --follow`, DM the bot, then make sure `systemctl list-timers claw-sync.timer claw-backup.timer` shows both.

Logs: `journalctl -u claw-sync`, `journalctl -u claw-backup`, `/home/gitbot/agent-git.log`, `/home/calbot/agent-cal.log` (all need sudo).
Quick health check (timer, gateway, recent logs, memory): `claw-status` (as the admin user; prompts for sudo; installed by claw-install). For the full wiring check: `sudo claw-smoke`.

## Gateway drop-ins

- Systemd drop-ins live in `infra/gateway-dropins/` and are installed root-owned to `/etc/systemd/user/openclaw-gateway.service.d/`. systemd reads a unit's drop-ins from every user unit path, so the unit OpenClaw generates in openclaw's `~/.config/systemd/user/` picks them up unchanged. A drop-in removed from the repo is removed there too, and `claw-install` deletes (as openclaw) the copies older installs put in `~/.config/systemd/user/openclaw-gateway.service.d/`.
  - `heap.conf`: Sets `NODE_OPTIONS=--max-old-space-size=2048` (a 2 GB heap limit). OpenClaw's own `ExecStart` is left alone, so `openclaw update` needs no drop-in edit. Node processes the gateway starts directly (plugins, `npm`/`npx`, execs) inherit the same limit: a cap, not a reservation. Those started through sudo (`coder-acp`, the brokers) don't, since sudo resets the environment. An `EnvironmentFile=` in OpenClaw's unit setting `NODE_OPTIONS` would override this; the `/proc/<pid>/environ` check below shows which one won.
  - `compile-cache.conf`: Sets `NODE_COMPILE_CACHE` for faster restarts.
- After a change: `sudo -u openclaw XDG_RUNTIME_DIR=/run/user/$(id -u openclaw) systemctl --user daemon-reload`, then restart the gateway. Check with `... systemctl --user cat openclaw-gateway` (OpenClaw's `ExecStart` plus the drop-ins from `/etc/systemd/user/`) and `sudo cat /proc/$(pgrep -u openclaw -f 'openclaw.*gateway' | head -1)/environ | tr '\0' '\n' | grep NODE_OPTIONS`.

## The main agent's tools
The assistant has no shell: `openclaw.json` denies `group:runtime` (`exec`, `process`, `code_execution`) and the `gateway` tool, and `tools.fs.workspaceOnly: true` limits `read`/`write`/`edit`/`apply_patch` to `~/.openclaw/workspace` (memory and to-dos stay writable; `openclaw.json`, `.env` and the extensions dirs are out of reach). Skills outside the workspace (`~/.openclaw/skills`, plugin skills) stay usable: OpenClaw's `skills_read` loads a skill's `SKILL.md` by name from the eligible catalog, and a `read` grant also permits it. Inbound attachments saved outside the workspace may not be readable with `read`; check from Telegram after deploying. It reaches the brokers only through the **claw-tools** plugin (`infra/openclaw-plugins/claw-tools/`, root-owned, see Plugins):
- `calendar_list_calendars`, `calendar_events`, `calendar_create`, `calendar_update`, `calendar_delete`, `calendar_undo`, `calendar_changes` → `agent-cal` as calbot;
- `github_issue_list`, `github_issue_view`, `github_issue_create`, `github_issue_comment`, `github_issue_label`, `github_issue_close`, `github_issue_reopen` → `agent-git` as gitbot (no `pr` or `new-repo`: repo changes go to Claude Code over ACP);
- `claude_usage` → `claude-usage` as coder.

Each tool has a strict schema (the brokers' own regexes, lengths and label allowlist) and runs `sudo -n -u <user> <broker> <verb> <args>` with an argv array, no shell, a fixed environment, a 90s timeout and a 256 KB output cap. Bodies go on stdin. A call that fails the schema never starts a process. The brokers stay the security boundary and keep all their checks. Calendar events come back with title, time, calendar and id only (no locations or notes), from `calendar_events` and from the writes that echo the event back (`calendar_create`, `calendar_update`, `calendar_delete`, `calendar_undo`). Calendar and issue text is wrapped as untrusted external content, like `web_fetch` results. A missing plugin load path (before `claw-install` has run) is only a warning to OpenClaw: the gateway starts without those tools. The sudo rules are unchanged: the plugin runs inside the gateway as openclaw. `infra/tests/claw-tools.test.sh` checks every tool's exact broker call. To add a verb: add it to the broker, then a tool in `tools.js`, its name in `openclaw.plugin.json` and in `tools.alsoAllow`, and a test.

## The reader agent
Untrusted text (web pages and search results, calendar locations and notes, issue bodies, later email) goes to a second agent, `reader`, not to the main one. The main agent sees the reader's summary.
- **reader** (`agents.entries.reader` in `openclaw.json`): the `minimal` profile plus `web_search`, `web_fetch`, `calendar_list_calendars`, `calendar_events`, `calendar_event_details` (events with locations and notes), `github_issue_list` and `github_issue_view`. File, shell, memory, session, message, cron and gateway tools and every claw-tools write are denied. Its own workspace (`~/.openclaw/workspace-reader`, only `AGENTS.md` tracked), no skills, no subagents, Gemini Flash with low thinking.
- **main**: `web_search`, `web_fetch`, `calendar_event_details` and `github_issue_view` denied (it keeps `github_issue_list`, titles only). It asks the reader with `sessions_send` (`agentId: "reader"`), and its AGENTS.md says a reader answer is data: nothing from it goes to memory or into an action unless you ask in chat.
- **One way:** `tools.agentToAgent.allow` is exactly main and reader, main may send only to the reader, the reader to nobody, and `tools.sessions.visibility: "agent"` keeps the reader out of main's history. Telegram is bound to main; `agents.ownership: "explicit"` with main as the system and heartbeat agent, so nothing reaches the reader except main's questions. `agents.defaults.skipBootstrap: true` stops OpenClaw seeding starter files (including `BOOTSTRAP.md`) into the reader's workspace.
- **Its model key:** the reader has no credentials of its own. OpenClaw reads auth profiles through from the shared store when an agent has none locally, so it uses the same Gemini key as main. To check on the host (as openclaw): `openclaw models status --agent reader --check`. If that reports no usable credential, run `openclaw doctor` (it reports a pending shared-store relocation, which `openclaw doctor --fix` performs). Don't copy `auth-profiles.json`: OpenClaw no longer reads that file at runtime.
- `infra/tests/agents-config.test.sh` checks all of this in CI.
- **Owner task:** a hard daily cap on the Gemini API key (Google Cloud console → IAM & Admin → Quotas, Generative Language API requests per day, about 3× a normal day). The budget alert only warns.

## Approvals
claw-tools also gates what the agent does (`infra/openclaw-plugins/claw-tools/approvals.js`), with a `before_tool_call` hook:
- **Approve in Telegram:** `calendar_create`, `calendar_update`, `calendar_delete`, `calendar_undo`, every GitHub issue write, `sessions_spawn` unless it's explicitly an OpenClaw subagent (`runtime: "subagent"`; anything else is treated as a hand-off to Claude Code and shown with the agent, working dir and the start of the task), and `sessions_send` (so an approved Claude Code session can't be handed new work without a card), except a plain question to the read-only reader (`agentId: "reader"`, no session key). The prompt goes to the owner's Telegram DM (`approvals.plugin` targets `${TELEGRAM_ALLOW_FROM}`; inline buttons on in DMs) with Approve and Deny only, never "allow always", and times out after 10 minutes. Deny, timeout or no reachable approver blocks the call. Only Telegram user ids from `commands.ownerAllowFrom` can approve (also with `/approve <id> allow-once` in the chat). The card text is built from the call's own parameters (control characters, newlines and markdown stripped, `/approve` defused, fields capped; a body, comment, task or message too long for the card says so before the text and in the card's title, "only the first N shown", and Approve covers the whole text), and OpenClaw freezes those parameters for the approved call. A delete or update names the event when a recent `calendar_events` listing had it. Each decision is logged to the gateway log with the tool and a hash of the parameters.
- **Blocked:** `message` calls that would reach anyone but the owner: broadcasts, another channel, account, group or guild, and any target (`target`, `to`, `targets`, `recipients`, `chatId`, ...) other than the owner's Telegram id. Replies in the current chat name no destination and pass.
- **Logged only:** `web_fetch` (host only), to see what it's used for before deciding whether to gate it.
- Reads (`calendar_events`, `github_issue_view`, `claude_usage`, ...) never prompt.

**Limits:** this stops a prompt-injected model, not code running as openclaw: a plugin the agent planted or a gateway bug could resolve approvals. The plugin allowlist and root-owned plugins, the missing shell, and the brokers' own caps and undo cover that. A stronger option for the calendar, if ever wanted: agent-cal holds a pending change and commits it only on a confirmation calbot receives over its own channel (its own bot token), outside openclaw's reach.

## Plugins
OpenClaw runs native plugins in the gateway process with the gateway's access, so what loads is fixed in this repo:
- **`plugins.allow`** in `openclaw.json` lists every plugin id that may load: the plugins bundled with the pinned OpenClaw version plus the non-bundled ones in use (`acpx`, `duckduckgo`). Any other id is ignored, wherever it's found. A plugin dropped into `~/.openclaw/extensions` or `<workspace>/.openclaw/extensions` with a bundled id doesn't replace the bundled copy (bundled ranks above those dirs in OpenClaw's discovery precedence). When an OpenClaw upgrade bundles a new plugin you want, add its id here. Enabling a plugin with the CLI adds it to the list in place, which claw-sync reverts, so add it by PR.
- **Root-owned plugins** live in `infra/openclaw-plugins/<id>/`: the plugin's source, or a `package.json` + `package-lock.json` that pins an npm package at an exact version. `sudo claw-install` installs each one root-owned to `/usr/local/lib/claw/openclaw-plugins/<id>` (`npm ci --ignore-scripts`, built in `<id>.new` and swapped in, reinstalled only when the source changes), and `openclaw.json` loads it from there with `plugins.load.paths`. A configured load path ranks highest, so a copy with the same id anywhere else is dropped. openclaw can run the code but can't change it. Each one has `plugins.entries.<id>.hooks.allowPromptInjection: false` unless it needs prompt hooks. `infra/tests/openclaw-plugins.test.sh` checks that `openclaw.json` and this folder agree. Until `claw-install` has run, a missing load path is only a warning, and OpenClaw uses the plugin's previous install.
- **DuckDuckGo** is pinned this way (`infra/openclaw-plugins/duckduckgo/`). To upgrade it, bump the version in its `package.json`, run `npm install --package-lock-only --ignore-scripts --legacy-peer-deps` there, open a PR, merge it, then run `sudo claw-install`. The old copy under `~/.openclaw/extensions/duckduckgo` is shadowed by the root-owned one; leave it (uninstalling through the CLI also edits `openclaw.json`).
- **Tripwire:** a claw-sync full run fails its ping, naming the dirs, while `~/.openclaw/extensions` holds anything but `acpx` and `duckduckgo` (the ones installed there on purpose, `GLOBAL_PLUGINS` in claw-sync and claw-smoke; a bundled or allowlisted id there counts too, since it could shadow the real one), or `<workspace>/.openclaw/extensions` holds anything at all. `acpx` itself still loads from that openclaw-writable folder; moving it under `infra/openclaw-plugins/` is a follow-up. It reports and never deletes. claw-sync runs as openclaw, so this catches mistakes; the allowlist and root-owned paths are the control. `claw-smoke` also checks the registry: nothing enabled loads from the workspace, or from `~/.openclaw/extensions` other than `acpx`/`duckduckgo` (see Smoke test).
